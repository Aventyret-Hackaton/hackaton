# From akka-tools to aventyret-rig — what is new

> This is the plugin `legacy`: everything the rig knows about akka-tools lives in
> this directory (tasks `proxy-legacy*`, the sidecar `legacy-attach`, this
> text). The plugin is removed when no site refers to `AKKA_TOOLS` in its
> compose any longer — then the `include:` line in the checkout's
> `compose.yaml` goes away too. Moved here from `docs/FROM_AKKA_TOOLS.md` 2026-08-30.

An introduction for developers who already know akka-tools. The focus is on
what is new and better, not on a full walkthrough. For machine setup see
[README.md](../../../README.md), for a step-by-step migration see
[MIGRATE_TO_RIG.md](../../../MIGRATE_TO_RIG.md).

## What was challenging about akka-tools

akka-tools was built for a narrower problem than the one we have today, and
some of the foundations chafed over time:

- **Sibling checkout over a relative path.** The site pointed at a local checkout
  via `AKKA_TOOLS=../akka-tools/`. Dockerfiles and makefiles were read *live* over
  that path. Every developer — and CI — had to have the repo checked out in the
  right place. Wrong directory name or a missing checkout, and nothing built.
- **Version drift.** Because the tooling was read live, there was no link
  between a site and a *specific* version of the tooling. Two developers with
  different `akka-tools` commits got different builds of the same site, and it
  did not show in the site's git history. "Works on my machine" became hard to
  troubleshoot.
- **Bound to the name and the idea "akka".** Everything was called `akka-*` — targets,
  env variables (`AKKA_TOOLS`, `AKKA_CERT`, `AKKA_MODULES`), mount points
  (`/akka/...`). In practice the tooling assumed an akka site (WordPress CMS +
  akka-modules), and supporting *other* stacks — plain Laravel, older WP,
  standalone frontends — meant bending a tool that was built for one thing.
- **Manual certificate handling.** Certificates were generated by hand and mounted via
  the `$AKKA_CERT` path. A new site or a new domain meant new certificate steps, and
  the site repo had to know a path into the akka-tools checkout.
- **DNS via `/etc/hosts`.** Every new `*.test` domain had to be added by
  hand to `/etc/hosts` (and/or to a domain list the proxy knew about). Easy
  to forget, easy to leave dead lines behind.
- **npm.** No supply-chain cooldown and silent postinstall scripts — npm's whole
  attack surface straight into the dev environment.
- **One big, condition-heavy base makefile.** `akka.mk` was a monolith where targets
  applied to every site and differences were handled with conditions. A site that was only
  a frontend still got CMS logic in its make namespace, and adding support
  for a new stack meant more branches in the same file.

## The big idea

The rig is an answer to exactly those points, and turns the basic model around.

**From sibling checkout to vendoring.** Instead of reading tooling live
from `../akka-tools/`, a copy is **committed** in the site repo under `.rig/`. The repo
becomes self-sufficient — the only thing required on the machine is that the shared
rig stack (proxy/dns/cert) is running. No shared checkout, no relative path
that has to be right.

**From drift to a tracked version.** `.rig/` carries `VERSION` + `MANIFEST`, so a
site is locked to an exact rig version that shows in git. Updating is a
deliberate, reviewable step (`rig self update`) — not something that happens to
differ between two machines.

**From "akka" to stack-neutral.** The name and the assumptions about akka are gone.
The rig is built to support several stacks side by side — each framework
lives in its own directory (`plugins/akka`, `plugins/wp`,
`plugins/laravel`) with its plugin.rig manifest, and shared services
(`db`, `redis`) live in `services/`. A site names its convention with
`RIG_STACK` — instead of a monolith makefile full of conditions, each
module gets its own file and registers itself.

The rig is also split into two clearly separated halves, which akka-tools
mixed together:

| | What | Where it runs |
|---|---|---|
| **Machine infra** | Traefik proxy, `*.test` DNS, automatic TLS certificates, shared caches | Once per computer (the rig repo, `rig proxy up`) |
| **Site tooling** | Dockerfiles + tasks per stack | Copied into each site repo under `.rig/` |

## Concrete improvements

### 1. Vendored `.rig/` with version tracking
- `.rig/VERSION` + `.rig/MANIFEST` (sha256 per file) → you can see exactly which
  rig version the site has.
- `rig self status` — compares the vendored version with the latest (fast `ls-remote`).
- `rig self update` — moves the pin to the latest release (`RIG_VERSION` in rigfile);
  the version is fetched once into the machine's cache and `.rig` is a symlink to it.
  (Since 2026-08-30 — the vendored `.rig/` copy with VERSION/MANIFEST and
  `FORCE=1` described elsewhere in this text is history.)
- Site deviations live in the site: `EXTRA_*` args, overlay, `rigplugins/`.

### 2. Automatic TLS certificates (`rig-cert`)
- In akka-tools you generated certificates manually and mounted them via the
  `$AKKA_CERT` path.
- Now the `rig-cert` service watches docker events. A container with the label
  `rig.hosts=mysajt.test,www.mysajt.test` gets a certificate issued within
  seconds, signed by the machine's mkcert CA, and Traefik hot-reloads it.
- The same label gives Traefik's router rule, so the domain is stated in one single place.
  Certificates persist in `.cert/share/sites/`.

### 3. Automatic `*.test` DNS (`rig-dns`)
- dnsmasq container + `/etc/resolver/test` (via `rig proxy dns-setup`) → **all**
  `*.test` points at localhost.
- No more `/etc/hosts` editing and domain lists. Does not affect
  VPN/corporate DNS (macOS only reads the resolver for that particular zone).

### 4. Certificates shared via a docker volume instead of a path
- `$AKKA_CERT:/akka/cert` → the external named volume
  `rig-cert:/rig/cert:ro`.
- The site repo needs **no env variables or paths** pointing at a
  rig checkout. The CA key never leaves `.cert/` (only public material is
  published).

### 5. Shared package caches across all sites
Three named volumes are created by `rig proxy up` and shared by all stacks — packages
are downloaded once, never again:

| Volume | For |
|---|---|
| `rig-composer-cache` | PHP images (cms, laravel, wp) |
| `rig-pnpm-store` | www **and** cms |
| `rig-npm-cache` | wp/laravel (npm; the wordpress theme is built with pnpm) |

All images run as `www-data` (uid 33, Debian bookworm) → no
ownership conflicts in the shared store.

### 6. npm → pnpm (www & cms)
- Tasks run pnpm, pinned via Corepack in the image
  (`COREPACK_DEFAULT_TO_LATEST=0`).
- **Supply-chain cooldown:** `minimumReleaseAge: 1440` in `pnpm-workspace.yaml`
  — does not install versions younger than 24h. This is the main reason for the switch.
- Build scripts must be allowlisted (`allowBuilds`) — no silent
  postinstall scripts.

### 7. akka-modules decoupled
- Gone: the `$AKKA_MODULES` mount and all `cms-link-akka-modules` /
  `akka-modules-sync` targets.
- akka-modules is now consumed as **published packages** — bump the version in
  `package.json`/`composer.json`.

### 8. Modular set of plugins
- `RIG_STACK=akka` selects the framework convention — the stack's manifest
  (`plugins/akka/plugin.rig`, a preset over `nextjs` + `wordpress`) declares which units and shared
  services are included. The task names are role names (`rig www install`,
  `rig cms build`, ...), the same on every site regardless of stack. `RIG_MODULES`
  adds extensions (`github`, `gcloud`, `worktree`, `deploy`); the build contract
  `ci` follows the stack.
- Modules register themselves in the aggregates → `rig
  setup`/`install`/`build`/`format` do the right thing for exactly the modules the site
  has enabled.
- `rig help` lists everything. `rig completion` gives tab completion even for
  dynamically loaded tasks.

### 9. Hardened non-root images
- www/cms/wp/laravel run non-root on Debian bookworm as `www-data`.
- nginx gets `cap_net_bind_service` via `setcap` → can bind 443 in the container
  (for container→container loopback) without root.
- Composer bumped (2.10.2), clean of PHP 8.4 deprecations.

### 10. Health check and fail-fast
- `rig proxy doctor` — checks Docker, disk, `.env` files, the rig network, DNS, ports
  and CA trust, with suggested fixes.
- `proxy check` — a cheap (~50ms) guard before `dev`/`up` that gives a clear error
  if the rig stack is not running (instead of a cryptic "network rig could not be
  found" or silent dead routes).

### 11. Performance: node_modules/.next as volume overlays
- Placed in volumes of their own on top of the bind mount → avoids slow
  macOS bind mount sync of thousands of small files, keeps the host directory clean and
  prevents Linux-native binaries (sharp, esbuild) from leaking out to
  host tooling.

### 12. Other
- Traefik **v3.6**, http→https redirect at entrypoint level, auto-TLS on all
  entrypoints.
- `rig self update /path/to/aventyret-rig` — pin a site to your checkout
  to test local rig changes (no commit/push).
- The network is now called `rig` (it was called `proxy` in akka-tools) — a common
  504 pitfall during migration if `.env` still says `NETWORK = proxy`.

## Moving to rig: step by step

Once per computer. The prerequisites are the same ones akka-tools already required:
Docker Desktop, mkcert, gh, git.

```bash
# Clone next to akka-tools (keep that checkout — the legacy sites still
# build their images from it)
cd ~/Developer
git clone https://github.com/Aventyret/aventyret-rig.git
cd aventyret-rig
./bin/rig proxy setup
exec $SHELL -l          # first time only: the PATH line was just added
```

One command, not six — and the same command a developer without akka-tools
runs. `proxy-setup` detects the sibling checkout and then takes the akka path instead
of the straight one:

1. **Preflight** on what we cannot fix for you: docker, mkcert, git,
   the daemon, and Docker Desktop's privileged port mapping (without it
   rig-dns cannot bind `127.0.0.1:53`). Fails before anything has changed.
2. **`rig` on PATH** — a symlink into the checkout, so `git pull` updates it.
3. **Inherits your root CA** from `akka-tools/.cert`, if the rig does not already have one.
   Then there is ONE CA on the machine: everything already issued stays valid,
   the keychain is already used to it, and `mkcert -install` never needs to ask
   for a password. Only the CA pair is copied — the leaf certificates are the rig's to reissue.
4. **`rig proxy legacy`** — takes over 80/443/53 from akka-proxy, includes the
   legacy domains in the default certificate, cross-trust between the CAs, starts the
   rig stack. See [transition mode](#transition-mode-unmigrated-sites-behind-the-rig-proxy).
5. **`*.test` DNS** against rig-dns (sudo). Expect it to ask: akka-tools
   has no DNS service; instead every `.test` domain is a line in
   `/etc/hosts`. The resolver replaces all of them — the old lines do no
   harm (they also point at 127.0.0.1) but can be removed. If you already have an
   `/etc/resolver/test` that is correct, the step is skipped entirely.
6. **`rig proxy doctor`** to finish.

Idempotent throughout: rerun whenever you like. If you still have akka-tools on disk but
no longer run anything from it — `./bin/rig proxy setup --fresh` skips steps 3–4 and
takes the ingress directly. The network `proxy` is created anyway, regardless of `--fresh` and regardless of whether
the checkout is found: it is the sites' network and not the akka-tools stack.

After that it is business as usual:

| | Command |
|---|---|
| Unmigrated (akka-tools) site | `cd ../minsajt && make up` — nothing more |
| Migrated (rig) site | `cd ../minsajt && rig setup` the first time, then `rig up` |

`rig proxy legacy` can be rerun at any time — e.g. when someone has added a
domain to akka-tools `domains.dat`, or if you recloned akka-tools and got a
new CA.

What is **not** included: any changes in the legacy sites' repos. See
[Should anything be committed in the legacy repo?](#should-anything-be-committed-in-the-legacy-repo) below.

## Transition mode: unmigrated sites behind the rig proxy

The migration happens site by site, but **the machine has only one ingress**: akka-proxy
and rig-proxy both want to own 80/443 (and the DNS servers 53). So it is not possible to
run both in parallel — and it is not needed. The rig proxy can serve unmigrated
akka-tools sites as they are:

```bash
rig proxy legacy            # finds ../akka-tools by itself, otherwise: rig proxy legacy <path>
```

The task does the machine-local things, idempotently:

1. **Stops** `akka-proxy` — and `akka-dns`/`akka-cert` if the checkout is one
   that has them (they do not exist in akka-tools as pushed). Reversible:
   `rig proxy down`
   + `make up` in akka-tools.
2. **The domains** from akka-tools `proxy/domains.dat` are merged into the rig's
   `ingress/traefik/domains.dat` and end up in the default certificate. These days mostly a
   safety net: `rig-cert` reads the domains directly from the router label (see below) and
   issues real per-site certificates for unmigrated sites too.
3. **Creates the network `proxy`** if it is missing. The legacy compose files declare
   their network `external: true` and it was owned by the akka-tools compose — if you have run
   `make down` there it is gone, and the site's `make up` dies on "network proxy
   declared as external, but could not be found". If the site has its own network name
   (`akka_network`, `<site>_network`) the fix is the same: `docker network create
   <name>`.

   The step is a task of its own, `rig proxy legacy-network`, and is also run by
   `rig proxy setup` and `rig proxy up` — even with `--fresh` and even when
   no akka-tools checkout is found, because a machine can have unmigrated sites
   without having the checkout next to it. Rerunning it every time is not
   overkill: the network is *unused* as long as no legacy site is running, so
   `docker system prune` takes it, and then the error is back. `rig
   proxy-doctor` warns when the network is missing.
4. **Cross-trust between the CAs.** The two checkouts have different mkcert CAs
   (unless you copied `.cert` when you set up the rig). The legacy CA is placed in
   `.cert/legacy-rootCA.pem` → comes along in the bundle that the site containers
   mount via `rig-cert`, and the rig's CA is placed in akka-tools
   `.cert/ca-bundle.crt`, which the legacy containers mount via `$AKKA_CERT`.
   After that a migrated and an unmigrated site can call each other over https.
   If both checkouts have the same CA the step is skipped.
5. **Connects running sites' ingress to the rig network** — and after that
   the `rig-cert` watcher handles it for you on every start (see below).

What does *not* need to be done: router labels. The legacy sites set explicit
`traefik.http.routers.*.rule`, and the rig's `defaultRule` only applies to containers
without a rule. The http→https redirect is now handled at entrypoint level, so
the catchall labels on the old proxy container are not needed.

### The network — connect the ingress, do not move the site

The rig proxy runs `--providers.docker.network=rig`. Traefik finds the container via
docker.sock regardless of network, but looks up the backend IP on the rig network — if the site
stays on `proxy`/`akka_network` there is no IP there, and the response is **404/504**.

The obvious fix (`NETWORK=rig` in the site's `.env`) is wrong, and it is worth
knowing why: the legacy compose files put *all* services on the same network, and
compose gives every service a network alias that is the service name. Two legacy sites
on `rig` therefore means two containers with the alias `db` on the same network — docker's
resolver answers with both IPs, and site A's `www` can read and write in site B's
database. Migrated sites avoid this by only putting the ingress services
(`www`, `cms`) on `rig` and internal traffic on their own default network.

The connection is therefore handled automatically, by the `rig-cert` watcher
([docker/attach/attach.sh](docker/attach/attach.sh)). On every docker
start event it sweeps all running containers, takes those that declare a
route (`traefik.http.routers.*.rule` or `rig.hosts`) and are not already
on `rig`, and runs `docker network connect`. That gives *no* service name alias —
only the container name, which is already site-prefixed — so `db`/`redis` stay
private.

The sweep takes the whole site at once (`www` and `cms` start within a second
of each other), and then restarts rig-proxy: `docker network connect` does
not give Traefik's docker provider a full container event, so it otherwise keeps
the old IP and answers 504. That is one restart per `compose up`, not one
per container.

Two properties worth knowing:

- **The watcher touches nothing when rig-proxy is not running.** If akka-proxy still owns
  the ingress on the machine nothing happens — it lacks
  `providers.docker.network`, so a container on two networks would have made its
  routing ambiguous.
- **It heals itself.** If you start a site while rig-proxy is down, it is connected
  when `rig proxy up` runs: the proxy's own start event triggers a new sweep.

`rig proxy legacy-attach` does the same thing manually — to connect directly without
waiting for an event, or when the automation is switched off (`RIG_ATTACH=0` for
the `cert` service in [compose.yaml](../../../compose.yaml)).

If you want it permanent for a site you have open anyway, it is four lines in
its `compose.yaml`: add the rig network and put only the ingress services on
both networks.

```yaml
networks:
  default:
    name: ${NETWORK:-akka_network}
    external: true
  rig:                     # ← add
    name: rig
    external: true

services:
  www:
    networks: [default, rig]   # ← only the ingress services, never db/redis
```

### What a developer does to run a legacy site

The site is untouched: `Makefile`, `.env`, `compose.yaml`, the akka-tools checkout and
the `$AKKA_CERT` mount work exactly as before. Only the ingress changes owner.

Once per machine (what you do anyway when you move to the rig):

```bash
./bin/rig proxy cli-setup     # rig on PATH
rig proxy up                  # the rig stack: proxy + dns + cert
rig proxy dns-setup           # the same /etc/resolver/test that akka-tools used
rig proxy legacy              # takes over the ingress from akka-proxy
```

Then, per legacy site — exactly as before:

```bash
cd ../dryckesbutiken.se
make up                       # unchanged: akka.mk, ${AKKA_TOOLS}, everything
```

Nothing more. The `rig-cert` watcher sees that `www`/`cms` started, connects them to the
rig network and reloads the proxy — within a couple of seconds, every time they are
recreated. `rig proxy legacy-attach` remains as the manual equivalent.

If you clone akka-tools fresh and run `make cert` there, a new root CA is created —
run `rig proxy legacy` again so the cross-trust is updated.

### Should anything be committed in the legacy repo?

**No.** Everything above is machine-local: the rig checkout, `.cert/`, docker networks.
The legacy repo gets zero diff during the transition.

And that is deliberate: if you commit the rig network in a legacy site's `compose.yaml`
it cannot be started by a colleague who is still running akka-proxy — the network
`rig` does not exist on that machine (`docker network create rig` rescues the start,
but akka-proxy has no `providers.docker.network` flag, so which of the
container's two networks it routes to is not guaranteed). The transition is per
developer, so the configuration belongs on the machine, not in the repo.

The exception is when the *whole* team has moved over for a given site: then
the compose variant above is right, and `proxy-legacy-attach` is no longer needed for
that site. But by then the next step is the real migration to
`.rig/` anyway, where the network convention is handled properly — see
[MIGRATE_TO_RIG.md](../../../MIGRATE_TO_RIG.md).

### Certificates for legacy sites — without touching the site

`rig-cert` issues certificates for containers with `rig.hosts`. An unmigrated site has
no such label — but it has already said which domain it is about:

```
traefik.http.routers.orisdental-cms.rule=Host(`cms.orisdental.test`)
```

The watcher reads hosts from that rule as a third domain source. The same truth that
Traefik routes on, so the certificate can never contradict the route, and the legacy site gets
exactly the same automatic per-site certificates as a migrated site — without a single
change in the site repo. `HostRegexp`/`HostSNI` are skipped (mkcert needs
literal names); they are covered by the default certificate via `domains.dat`.

**Run `rig proxy legacy` anyway.** The certificates above are signed by the *rig's* CA, and
a legacy container only has the akka CA in its `ca-bundle.crt` — every https call
it makes to its own public domain blows up otherwise. The cross-trust in step 4 is
what solves it.

### Left to do by hand

Static routes in akka-tools `proxy/dynamic/traefik.yaml` (e.g. `*.thingwalla.test`
→ `host.docker.internal:30080`) do not come along — the file also carries a tls block
that points at the akka certificates. Copy only the `http:` block to
`ingress/traefik/dynamic/legacy-routes.yaml`; Traefik hot-reloads it.
`rig proxy legacy` tells you when it sees such routes.

## Quick mental model for an akka-tools developer

| akka-tools | aventyret-rig |
|---|---|
| `AKKA_TOOLS=../akka-tools` (shared checkout) | `.rig/` committed in the site |
| `include ${AKKA_TOOLS}/makefiles/akka.mk` | `RIG_STACK=akka` + `rigfile` |
|  `.rig/plugins/nextjs/docker/www` | `.rig/plugins/nextjs/docker/www` |
| `$AKKA_CERT:/akka/cert`, manual certificates | `rig-cert:/rig/cert:ro` + label `rig.hosts` |
| nginx snippets in `cms/.akka/`, `wp/.akka/` | the same files in `cms/.rig/`, `wp/.rig/` |
| `$AKKA_MODULES` mount + link targets | published packages |
| npm | pnpm (with cooldown) |
| `/etc/hosts` editing | `*.test` DNS via rig-dns |
| `akka-setup/update/status` | `rig setup`, `rig self update`, `rig self status` |
| No version tracking | `RIG_VERSION` in rigfile + `.rig/PIN` |
